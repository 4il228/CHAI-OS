# AGENTS.md: Ролевая модель и протокол оркестрации автономных агентов

Данный документ определяет архитектуру взаимодействия, зоны ответственности, правила изоляции контекста и порядок работы с удаленным репозиторием проекта **CHAI OS** для автономных ИИ-агентов.

---

## 1. Общие принципы и безопасность (Zero-Trust Context)

* **Принцип наименьшего контекста (Least Privilege Context):** Ни один агент не имеет права анализировать проект целиком. Доступ к файлам спецификаций и исходного кода строго разграничен. Нарушение границ доступа ведет к немедленному прерыванию сессии (с кодом `InstallerError::InvalidTarget` или эквивалентным сбоем изоляции).
* **Связь с базовыми спецификациями:** Все агенты обязаны руководствоваться архитектурными принципами, заложенными в `SPEC.md`, а также правилами безопасности из `SECURITY_PLAN.md`.
* **Запрет на дублирование:** Запрещено повторно описывать технические спецификации модулей. Агенты должны использовать ссылки на контракты спецификаций в соответствующих `*_PLAN.md` файлах.

---

## 2. Матрица ролей и разграничение доступа к файлам

Для реализации CHAI OS выделяются 4 независимых агента. Каждый агент инициализируется в изолированном окружении (песочнице) с доступом **только** к разрешенным файлам.

| Роль агента | Разрешенные файлы для чтения (Контекст) | Целевой репозиторий / Путь |
| --- | --- | --- |
| **Core & Security Agent** | `SPEC.md`, `CORE_PLAN.md`, `SECURITY_PLAN.md` | `/src/chai-core/`, `/src/ebpf/` |
| **UI/UX Shell Agent** | `SPEC.md`, `SHELL_PLAN.md` | `/src/chai-shell/` |
| **Infra & ISO Agent** | `SPEC.md`, `INFRASTRUCTURE_PLAN.md`, `ISO_BUILD_PLAN.md` | `/modules/`, `/flake.nix` |
| **Bootstrap & Installer Agent** | `SPEC.md`, `INSTALLER_PLAN.md` | `/src/installer/` |

> ⚠️ **СТРОГОЕ ПРАВИЛО:** Попытка чтения файлов, не входящих в разрешенный список для конкретной роли (например, чтение `SHELL_PLAN.md` агентом *Core & Security*), является нарушением безопасности Ring 0 на уровне абстракции разработки.

## 3. Инструкции и регламент работы для агентов

### 🤖 3.1. Core & Security Agent

* **Задача:** Разработка управляющего демона на Rust (`chai-core`) и eBPF LSM модуля безопасности.
* **Правила работы:**
* Реализовать строго асинхронный JSON-RPC 2.0 сервер по контракту из `CORE_PLAN.md` (Подфаза 1.2).
* Запрещено использовать динамические библиотеки; сборка обязана быть статически линкованной (`+crt-static`).
* Принудительно применять eBPF LSM-фильтрацию для изоляции путей, отличных от `/etc/nixos/` и `/tmp/chai-generation/`.



### 🤖 3.2. UI/UX Shell Agent

* **Задача:** Разработка REPL-интерфейса `chai-shell`.
* **Правила работы:**
* Интерфейс строго оформляется в цветовой палитре *Catppuccin Mocha* с использованием Unicode-символов (`⚡`, `❄️`, `🔍`).
* Реализовать двухрежимный парсер (POSIX с префиксом `!`, ИИ-интент — без префикса).
* Обязательно имплементировать модуль Graceful Degradation: при таймауте сокета автоматически дампить логи `journalctl -xe` и переводить TTY в rescue-режим.



### 🤖 3.3. Infra & ISO Agent

* **Задача:** Декларативная база NixOS, интеграция Ollama и сборка финального ISO.
* **Правила работы:**
* Вся конфигурация пишется исключительно через Pure Nix Flakes (`flake.nix`). Никаких императивных `nix-env`.
* Упаковать веса модели `Qwen-2.5-Coder` внутрь SquashFS образа для обеспечения offline-ready инференса.
* Валидация сборки проводится строго через автоматический запуск в QEMU (`ISO_BUILD_PLAN.md`, подфаза 6.3).



### 🤖 3.4. Bootstrap & Installer Agent

* **Задача:** ИИ-парсер дисковой разметки и оркестрация `nixos-install`.
* **Правила работы:**
* Интегрировать LLM-парсер ввода пользователя в валидный JSON-план.
* **Human-in-the-Loop:** Перед выполнением `parted` или `cryptsetup` агент *обязан* приостановить выполнение, сгенерировать UI-блок с diff-изменениями и ожидать байт `Y` (Raw Mode) от оператора.

## 4. Протокол работы с удаленным репозиторием

Все агенты ведут разработку в едином удаленном репозитории: `https://github.com/4il228/CHAI-OS`.

### 4.1. Разветвление (Branching Strategy)

Запрещено делать коммиты напрямую в ветку `main`. Каждый агент работает в своей изолированной ветке:

* `Core & Security Agent` ➔ `feature/core-ebpf`
* `UI/UX Shell Agent` ➔ `feature/chai-shell`
* `Infra & ISO Agent` ➔ `feature/nix-infra-iso`
* `Bootstrap & Installer Agent` ➔ `feature/installer-bootstrap`

### 4.2. Алгоритм атомарного коммита (Git Workflow Contract)

При завершении выполнения любой *Подфазы* (например, подфазы 1.1, 2.1 и т.д.) агент обязан выполнить следующий атомарный цикл:

1. **Локальная валидация:** Проверить код на синтаксис и успешность компиляции.
2. **Синхронизация:** Выполнить `git fetch origin` и `git rebase origin/main` для минимизации конфликтов.
3. **Фиксация:** Создать коммит со строго структурированным сообщением:
```text
feat(subphase-<номер>): <короткое описание выполненного контракта спецификации>

- Ссылка на план: <ИМЯ_ПЛАНА>.md (Подфаза X.X)
- Что сделано: <краткий список изменений>

```


4. **Пуш:** Выполнить `git push origin feature/<имя_ветки>`.
5. **Pull Request:** Автоматически сформировать PR в ветку `main`. Слияние (Merge) происходит только после прохождения CI/CD тестов (валидация в QEMU для ISO или успешный `cargo test`).
